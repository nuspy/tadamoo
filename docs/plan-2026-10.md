# Plan: harness robustness, Target Loop, intake and clarification, long answers, coding mode

Owner request of 2026-10-29: build everything the harness study proposes, plus the Target Loop, prompt handling with
clarification questions and next-prompt suggestions. This plan splits the work into tracks that can run in parallel in separate
worktrees off `next/integration`, then merge in a fixed order. The studies are in [harness-study/](harness-study/README.md).

## Rules for every track

- The rules of `AGENTS.md` and `CONTRIBUTING.md` apply: terse stateless comments, log lines through the logging module, no shims,
  docs under 300 lines, EN and IT strings for every visible text, every Settings control explained, 30 px minimum buttons, no
  horizontal scroll at 1024 px, keyboard operable.
- Every change has CPU-only tests (scripted mock engine). Anything that needs the real model or the GPU goes to
  `tests/QUEUE_daytime.md`; no track uses the GPU. GPU use is coordinated with the other session before and after.
- A track works in its own worktree and branch (`next/track-<name>`), commits only its own files, and never pushes. The harness
  numbers are development A/Bs and labelled with the GPU power limit.
- Unattended runs never block on a question: they auto-pick the recommended option and park only people, bookings and
  uncontrolled resources. The person chooses their own risk: offer every level, say the risk once.

## Tracks

**Core (first).** `harness/agent_loop.py`, `client.py`, `stack.py`, `registry`, `skills.py`, `context.py`:
read `finish_reason` and continue on `length` (at most 2-4, flagged "cut"), retry an empty reply once at lower reasoning effort,
a repetition guard, stop forcing temperature 0, always register `present_plan` and order tool schemas by volatility, a notice when
AGENTS.md is cut at 32 KiB and a total size per pinned block in `/context`, tool-call repair (JSON, schema-guided coercion,
tool-name repair, mixed batches), untrusted-content hardening (random boundary id, Unicode fold, control-token scrubbing),
execution-bias block measured with `harness.eval`.

**Tools.** `harness/tools/filesystem.py`, new `editing.py`, `search_code`, `tree`: `edit_file` with `edits[]`, a unique-match
tolerance cascade, "did you mean" errors with line numbers, read-before-write and stale-overwrite guard, syntax check after an
edit, `read_file` indentation mode, `search_code` (pure Python, gitignore-aware), `tree` with line counts.

**Target Loop.** A loop that executes, verifies that the target is fully met, and otherwise asks the model how to correct the unmet
part and resumes. Button "Target Loop" in the GUI chat and in the Agent tab, a dialog with a large text area and list tools,
target split into tasks and sub-tasks through the existing task registry (`serve/tasks.py`), achieved items struck through in red
with notes, history of the session's targets. Details below.

**Intake and clarification (after the two studies land).** A prompt-intake pipeline (cheap checks, a grammar-constrained triage
call, cleaning that never rewrites what is shown or stored, clarification, decomposition) and `ask_user` v2 with single, multiple
and free-text answers, an automatic recommended default for unattended runs, and next-prompt suggestions.

**Gate and hooks.** Post-tool feedback and a Stop hook, a verify gate with the project's own commands, a stronger loop guard
(result hash, cycles, progress reset, identical-result stubs), a budget warning with a grace call, the error classifier (needs the
owner's decision), `todo_write`.

**Long answers.** `serve/longform.py` and the `long_answer` request field (see [harness-study/long-answers.md]
(harness-study/long-answers.md)): visible `length` with a Continue button, `max_answer_tokens`, a multi-token loop guard, then the
segmented mode.

**Compaction.** Token-based cut points, a summariser that works inside one long turn and keeps the newest text, an identifier
audit, an explicit prefix-cache report.

**Coding mode.** Roles, the coding tool profile, the project profile and the safe-verification permission class, the Agent-tab
selector (see [harness-study/vibe-coding.md](harness-study/vibe-coding.md)).

## Order and merging

1. Core, Tools and Target Loop run at once. Merge order: Core, then Tools, then Target Loop (it touches the most GUI files); each
   merge runs the full `serve/tests` and the harness tests.
2. Intake and clarification and Gate and hooks start from the merged result (they touch `agent_loop.py` and the Agent tab).
3. Long answers and Compaction next, then the Coding mode.
4. After each merge a rebuild of the setup with `compile_and_package.ps1`, only when the owner is not using the GPU.

## Target Loop: specification

- **Where.** A "Target Loop" button next to the send button in the GUI chat and in the Agent tab. It opens a dialog.
- **Dialog.** A large text area (at least 60% of the window height, resizable, monospaced off) for a long description. Buttons
  for a numbered list and a bulleted list, and automation: Enter at the end of a list line starts the next item (next number or the
  same bullet), Enter on an empty item leaves the list, Tab and Shift+Tab indent and outdent, pasted multi-line text is
  recognised as a list. The same list helpers are added to the normal prompt boxes (chat and Agent).
- **Posting.** The text is sent to the chat as a normal prompt (the person sees it as their message); the dialog keeps the target as
  a checklist. Items already achieved are struck through in red; each item has notes (exceptions, problems, modifications,
  evidence). The dialog also shows the tasks and sub-tasks derived from the target and their state.
- **History.** The dialog keeps every earlier target of the session (text, final state, per-item result, iterations), so the person
  can see what was done and reuse a target.
- **Loop.** Split the target into criteria and the tasks and sub-tasks that serve them (grammar-constrained JSON; stored in the
  existing task registry and shown there too). Execute task by task, sending each as its own focused prompt with only the needed
  context. After each pass, verify: a grammar-constrained judge call returns per-criterion `{id, status achieved|partial|not_met|
  blocked, evidence, missing}`, plus deterministic checks where they exist (the project's verify commands, files expected to exist,
  tests). All criteria achieved: close the loop. Otherwise ask the model how to correct or improve only the unmet part (what is
  missing, why the last attempt did not meet it, what to change), make new tasks for it, and resume. Never redo what is achieved.
- **Stop rules.** The person can stop at any time. A stall detector (the same unmet items with the same evidence for N passes,
  default 3) makes the model propose a different approach once, then stops with a clear report; no other artificial cap, the
  person sets one if wanted. A blocked criterion (needs a person, a booking or an uncontrolled resource) is parked and the rest
  goes on; unattended runs never block on a question.
- **Honesty.** The judge sees the evidence (tool results, file diffs, test output), not only the model's claim; "achieved" without
  evidence is downgraded to "partial".
